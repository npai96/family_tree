## Reproduction sequence and safety check

1. Use a disposable local database and the review/test identity mode only on localhost. Populate **only** the fictional users and circles above; never copy a production database.
2. Run the focused API/frontend security tests and record the exact commit and commands. If a provider-level claim is made, run it against a disposable Postgres/Supabase project with the production-equivalent role, then remove its credentials from the shell history/capture.
3. Take `01` from local browser contexts; create `02`, `03`, `05`, and `06` from controlled tests and sanitized configuration. Render `07` from the checked-in Mermaid source. Create `08` only after cookie/CSRF tests pass and its value can be safely hidden. Create `04` only after per-circle RLS is implemented and verified.
4. Open each PNG at original resolution. Search visually for actual names/emails, photo content, account IDs, project refs, session tokens, JWTs, API keys, URLs with query tokens, database credentials, medical notes, and raw logs. Replace unsafe captures with a labeled synthetic mock or leave the planned file absent.
5. In the implementation report, list each captured asset and the specific control/test it depicts. A planned filename is not evidence that the screenshot exists.
